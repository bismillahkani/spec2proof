# Spec2Proof: connect the plugin first, then add a self-healing agent workflow

## Current status

The standalone app executes real Python tests, but requirement compilation, diagnosis, and repair are fixed templates. The current adapter is a small handwritten stdio server with MCP App HTML and OpenAI sidebar/conversation-panel metadata. It has not been installed or rendered inside ChatGPT.

The target is the user's personal ChatGPT account. The user confirmed OpenAI Platform billing and permission to create API keys are ready. No API key or tunnel runtime key is present in the execution session. The browser's Platform session is currently at login, so organization permissions have not been inspected. These are separate facts: a key may exist in the user's account without being available to this app.

## First milestone: a working personal ChatGPT plugin

Use a **private Secure MCP Tunnel** for development. This avoids public hosting during setup. Public directory submission is a later path that requires a stable HTTPS MCP endpoint and the applicable review/authentication requirements. See [Connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt) and [Secure MCP Tunnel](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels).

### Local readiness

Run `scripts/plugin_preflight.py` with the bundled or selected Python interpreter. It generates `.local/mcp.local.json` with an absolute executable, absolute launcher, and shared absolute data directory. The configuration is ignored by Git because it contains machine-specific paths. `scripts/mcp_entry.py` starts the checkout from any directory without requiring package installation.

This fixes the current configuration's reliance on `python` being on PATH and on matching working directories. The preflight verifies initialize, tool discovery, the two entrypoints, and the UI resource through an actual stdio subprocess. It prints only whether credential variables exist, never their values.

Before accepting the plugin as complete, replace the handwritten protocol/bridge with the official MCP server and MCP Apps SDKs, or verify interoperability with official clients and the actual host. The current local tests do not prove full protocol compatibility. The resource's initialization handshake, extension discovery, tool results, resize behavior, and sandboxed navigation need a host check. [Official UI guide](https://developers.openai.com/plugins/build/chatgpt-ui), [extension metadata](https://developers.openai.com/plugins/build/extensions).

### Account and tunnel setup

1. Sign in to [Platform tunnel settings](https://platform.openai.com/settings/organization/tunnels) using the relevant personal Platform organization.
2. Confirm **Tunnels Read + Manage** for creating/editing the tunnel and **Tunnels Read + Use** for running/selecting it. API-key creation permission alone does not prove these grants.
3. Create a development tunnel and associate it with the personal ChatGPT workspace. The exact workspace options must be verified in the account UI.
4. Download the official `tunnel-client` from the link in Platform settings/current documentation. It is not installed on PATH in this environment.
5. Configure the documented local-stdio profile, with `--mcp-command` equal to the absolute command generated by preflight. Provide its runtime credential locally through the documented environment mechanism; do not paste it into a chat or commit it.
6. Run `tunnel-client doctor --profile local-stdio --explain`, then `tunnel-client run --profile local-stdio`. Keep that process running.
7. In ChatGPT Plugins, add a custom MCP server, choose Tunnel, select its ID, review the requested permissions, create the personal plugin, and install it. Account policy may still restrict custom connections.

The current tunnel requirements and workspace associations are documented [here](https://developers.openai.com/api/docs/guides/secure-mcp-tunnels). Plugin permissions inside ChatGPT do not grant Platform tunnel permissions.

### Acceptance test inside ChatGPT

- Open Spec2Proof from the sidebar and beside a conversation.
- Create a 14-day refund proof and inspect the structured contract.
- Confirm the contract and execute the actual baseline: 8/10 pass.
- Propose the two-line patch. The agent must report a pending proposal, not an applied repair.
- Review/approve in the local browser using the same proof store; retrieve the resulting 10/10 evidence from ChatGPT.
- Refresh/reopen the panel and verify the same proof ID and frozen test hash.

This finishes the plugin milestone only after live host evidence exists. The current approval/download flow goes out to localhost and is unsuitable for someone using ChatGPT on another machine. The advanced panel should bring authenticated approval into the panel through a dedicated app-visible action and server-enforced authorization; hiding a tool from the model is not an authorization control.

## Second milestone: API-powered self-healing

### Architecture

React/TypeScript MCP App UI → official MCP adapter → durable job coordinator → OpenAI Agents SDK specialists → isolated Python execution → proof store.

Keep Python for the existing proof engine and agent backend. Add React for a richer panel: stage timeline, live events, agent outputs, code/test tabs, patch comparison, approval, and evidence export. Run long jobs asynchronously so an MCP call returns a job ID promptly; the panel reads progress and the server persists checkpoints.

The [Agents SDK](https://developers.openai.com/api/docs/guides/agents/sdk) supports application-owned tools, runtime behavior, and approval decisions. Use a manager-style workflow or code orchestration with specialists, as described in [Orchestration and handoffs](https://developers.openai.com/api/docs/guides/agents/orchestration). Resolve the actual model through the user's Platform access and a small task benchmark before choosing defaults; make it configurable.

### Specialist roles

| Role | Input | Output | Authority |
| --- | --- | --- | --- |
| Specification agent | Business requirement and supplied context | Typed acceptance contract, ambiguities, assumptions | Can request clarification; cannot modify code |
| Test agent | Approved contract | Executable tests linked to criterion IDs | Creates tests before the repair loop |
| Repair agent | Source snapshot, frozen tests, actual failure logs | Minimal candidate diff and explanation | May edit candidate source inside the isolated workspace |
| Review agent | Requirement, contract, tests, diff, run evidence | Risk findings and approve/revise recommendation | Cannot approve on behalf of the human |

The coordinator owns state, retries, budgets, artifact hashes, and the final result. The execution runner is deterministic infrastructure, not a model pretending to run tests.

### Healing loop

1. Analyze the requirement; ask for clarification where behavior is ambiguous.
2. Show the contract for approval, then generate, validate, and freeze the tests.
3. Run the baseline in an isolated environment and save its output.
4. Have the repair agent propose a candidate patch.
5. Apply that candidate only inside an ephemeral execution workspace; run frozen acceptance tests and existing regression tests.
6. On failure, return actual logs to the repair agent and repeat, with a proposed maximum of three repair attempts and explicit time/model-call/token limits.
7. Have the independent review agent inspect the successful candidate. Block patches that weaken tests, disable checks, or introduce unrelated changes.
8. Present the final diff and all attempts to the human. After approval, apply the exact approved patch to the target checkout, verify its base hash, and rerun.
9. Export a proof bundle containing requirement/contract versions, tests, baseline, all candidates, logs, review, approval, final rerun, trace IDs, and usage.

If a candidate passes its tests but the reviewer rejects it, produce a revised candidate within the same budget. If the budget is exhausted, report the unresolved failures and preserve artifacts. Never silently regenerate weaker tests to reach green. A test correction needs a new visible contract/test version and re-approval.

### Execution and approval boundaries

LLM-generated tests and source are untrusted code. The current local subprocess is not sufficient isolation for them. Use a supported hosted sandbox or a locked-down container worker with bounded CPU/memory/time, no credentials, and network disabled by default. A repository import must be an explicit selected snapshot, with limited paths and no access to the rest of the user's machine.

The loop can try and reject candidate patches in the disposable workspace automatically. Applying a patch to the user's actual repository remains an explicit approval tied to the base snapshot and patch hash. This makes the loop useful without treating a model's reviewer recommendation as human authorization.

### Build sequence and exit criteria

1. **Connection:** private plugin can call tools and render its panel in ChatGPT.
2. **Protocol/UI:** official SDK adapter plus richer React panel; approval authorization verified.
3. **Real reasoning:** API spec/test generation for several business domains, with structured outputs and traceable criterion coverage.
4. **Real repair:** imported Python snapshot, isolated runner, repair/review specialists, bounded retries.
5. **Resilience:** persisted jobs, reconnect/resume, cancellation, rate-limit recovery, usage visibility, reproducible proof export.
6. **Evaluation:** multi-domain fixtures, different defect classes, ambiguous requirements, unfixable cases, attempts to change tests, stale approval, and interrupted runs.

Deliverable for the first agentic version: a real model analyzes a new requirement, creates tests, repairs a new defect through at least one observed iteration, pauses for approval, and produces reproducible final evidence. No hard-coded repair or fabricated test result should satisfy this check.
